# grill-me — 만들기 전에 기획 털기

> 교육용 한국어판. 원본: Matt Pocock `mattpocock/skills`의 `grill-me` + `grilling` (MIT License, 원문은 `_원본/mattpocock-skills/`).
> 바꾼 점:
> - 원본은 `grilling` 스킬을 다시 부르는데, 이 파일 하나로 동작하도록 합쳤다.
> - 비개발자 수업용으로 라운드당 질문 수를 줄였다.
> - 하위 에이전트로 사실을 조사하는 부분을 "직접 파일 읽기"로 바꿨다.

사용자와 **같은 그림을 그릴 때까지** 인터뷰한다. 코드는 만들지 않는다.

## 진행 방식

1. 사용자가 준 기획(예: `@기획.md`)과 폴더 안 파일을 먼저 읽는다.
2. 기획을 **결정 나무**로 본다. 결정 하나에는 그 결정에 달린 다음 결정들이 가지처럼 붙어 있다.
3. **라운드** 단위로 묻는다.
   - 지금 바로 물을 수 있는 질문만 묻는다. 앞선 답이 정해져야 물을 수 있는 질문은 다음 라운드로 미룬다.
   - 한 라운드에 질문은 **최대 3개**다(사용자가 다르게 정하면 따른다).
   - 질문마다 번호를 붙이고 **추천 답**을 함께 준다.
   - 답을 받기 전에는 다음 라운드로 넘어가지 않는다.
4. 파일에서 확인할 수 있는 **사실**은 사용자에게 묻지 말고 직접 찾는다. 사용자에게는 **결정**만 묻는다.
5. 답이 쌓이면 나무를 다시 그리고 다음 라운드를 묻는다.
6. 빈 가지가 없거나, 사용자가 정한 질문 수에 도달하면 끝낸다.
   - 마지막에는 정해진 것, 아직 열린 것, 일부러 뺀 것을 요약한다.
   - 사용자가 요청하면 기획 파일을 고친다.
   - **사용자가 "이해가 맞다"고 확인하기 전에는 아무것도 만들지 않는다.**

## 라운드 형식

```
❓ **Q1** - **<질문 제목>**: <질문 내용. 보기가 있으면 보기도>

➡️ 추천: <추천 답과 한 줄 이유>

---

❓ **Q2** - **<질문 제목>**: <질문 내용>

➡️ 추천: <추천 답과 한 줄 이유>
```

## 잘 캐묻는 질문의 예

- **누가·어디서**: 장갑 낀 손으로도 누를 수 있어야 하나요? 화면 크기는 폰인가요?
- **예외**: 사진 없이 저장해도 되나요? 같은 설비를 하루 두 번 점검하면 어떻게 되나요?
- **경계**: 이번 버전에서 일부러 안 하는 것은 무엇인가요(로그인, 서버, 공유)?
- **완료 기준**: 무엇이 되면 "다 됐다"고 말할 수 있나요?

## 하지 않는 것

- 코드 작성, 파일 생성, 설치 — 사용자가 확인하기 전에는 하지 않는다.
- 한 번에 많은 질문을 쏟아내기.
- 사용자가 정할 결정을 대신 정해 버리기.

# brainstorming — 만들기 전에 같이 설계하기

> 교육용 한국어판. 원본: Jesse Vincent `obra/superpowers`의 `brainstorming` (MIT License, 원문은 `_원본/obra-superpowers/`).
> 바꾼 점:
> - git 커밋·worktree, 테스트 먼저(TDD), 시각 도우미 브라우저, 다른 스킬 자동 호출을 뺐다.
> - 화면·로컬만 만드는 비개발자 수업에 맞춰 줄였다.
> - 핵심은 남겼다: **의도 확인 → 설계 → 승인 전에는 만들지 않기**.

아이디어를 사용자가 알아보고 고칠 수 있는 **설계**로 바꾼다.

## 꼭 지킬 것

<HARD-GATE>
사용자가 설계를 승인하기 전에는 코드 작성, 파일 생성·수정, 설치를 하지 않는다.
폴더 안 파일을 **읽는 것**은 해도 된다.
</HARD-GATE>

"너무 간단해서 승인까지 필요 없다"는 생각이 들어도 짧은 설계를 보여주고 승인을 받는다.

## 순서

1. **폴더 둘러보기**: 관련 파일(기획.md, 기존 앱 폴더)을 읽고, 지금 무엇이 있는지 짧게 정리한다.
2. **의도 확인**: 무엇을 이루려는지, 누가 쓰는지, 무엇이 되면 성공인지 확인한다.
   - 모르는 게 있으면 **한 번에 질문 하나**만 한다.
   - 이미 답이 나와 있으면 다시 묻지 않는다.
3. **내가 이해한 것 써 보기**: 목표·조건·성공 기준을 5줄 안쪽으로 쓴다.
   - "사용자가 말한 것"과 "내가 가정한 것"을 나눠서 쓴다.
   - 사용자의 정정을 받고 반영한다.
4. **방법 2~3개 비교**: 장단점을 한 줄씩 쓰고 추천 하나를 고른다.
5. **설계 보여주기**: 승인 전에 아래 항목을 쓴다.
   - 화면 구성(탭·카드·버튼)
   - 데이터를 어디에 어떻게 저장하나(오늘은 브라우저 저장)
   - 기존 조각에서 그대로 쓰는 것 / 바꾸는 것 / 버리는 것
   - 이번에 **안 하는 것**
6. **승인 받기**: "이 설계로 갈까요?"라고 묻는다.
   - 승인 범위를 넘겨짚지 않는다. 설계 승인은 "계획을 써도 된다"는 뜻이지 "만들어도 된다"는 뜻이 아니다.
7. **설계 문서 저장**: 승인된 설계를 `docs/설계.md`에 저장한다.
   - 다음 단계는 `/writing-plans`로 계획을 쓰는 것이라고 안내한다.

## 하지 않는 것

- 승인 전에 만들기 시작하기
- 질문 여러 개를 한꺼번에 묻기
- 사용자가 말하지 않은 기능을 슬쩍 넣기
- 서버·데이터베이스·로그인 추가 — 오늘 수업 범위 밖이다. 사용자가 요구하면 "오늘 범위 밖"이라고 알린다

# writing-plans — 작은 단계로 계획 쓰기

> 교육용 한국어판. 원본: Jesse Vincent `obra/superpowers`의 `writing-plans` (MIT License, 원문은 `_원본/obra-superpowers/`).
> 바꾼 점:
> - git 커밋, worktree, 테스트 코드 먼저(TDD), 하위 에이전트 실행 안내를 뺐다.
> - 대신 단계마다 사람이 **localhost에서 눌러 보고 확인할 것**을 쓰게 했다.

이 프로젝트를 처음 보는 사람도 그대로 따라 할 수 있게 계획을 쓴다. 계획에는 **무엇을 정했는지**를 남긴다: 어떤 파일, 어떤 이름, 설계의 어떤 값, 어떻게 확인할지.

## 시작 전

- `docs/설계.md`(brainstorming 결과)나 사용자가 준 설계를 읽는다.
- 설계가 없으면 먼저 `/brainstorming`을 권한다.
- 설계가 너무 크면 나눠서 계획하자고 제안한다.

## 계획 문서 형식

`docs/계획.md`에 저장한다.

```markdown
# [기능 이름] 실행 계획

**목표:** 한 문장
**설계 문서:** docs/설계.md
**지킬 것:** 서버·DB 없음, 브라우저 저장만, 기획.md에 없는 기능 넣지 않기

## 파일 지도
- `index.html` — 무엇을 담당
- `app.js` — 무엇을 담당

## 단계 1: [이름]
- [ ] 할 일: 무엇을 어떤 파일에서 바꾸나 (구체적으로)
- [ ] 확인: localhost에서 무엇을 누르면 무엇이 보여야 하나
- [ ] 멈춤: 사용자 확인을 받고 다음 단계로

## 단계 2: ...
```

## 단계 크기

- 단계는 **3~5개**로 한다. 사용자가 개수를 정하면 따른다.
- 한 단계는 **눌러서 확인할 수 있는 변화 하나**만 담는다.
- 단계마다 "확인"을 반드시 쓴다. 확인할 수 없으면 너무 크거나 모호한 것이다.

## 스스로 점검 (저장 전에)

- 설계의 모든 항목이 어느 단계에 들어갔나?
- "알아서 적당히", "필요하면" 같은 빈 말이 남아 있지 않나?
- 단계 사이의 이름(파일명·버튼 이름)이 서로 맞나?

## 저장 후

계획 위치를 알리고 묻는다. "단계 1부터 시작할까요? 단계마다 멈춰서 확인받겠습니다."
**사용자가 시작하라고 하기 전에는 만들지 않는다.**
